# Research: typed read for a project's unvalued / untriaged issues (aw4)

Question from the plan (p_1m8087f4mb080s3azbqdxk): which typed-read shape in aw4's issue
tool surface lists a project's unvalued and/or untriaged issues in one fast call, so PM
desk sessions stop hand-rolling SQL over the raw events table — and is a fast indexed read
even possible, or must the read fold events?

All findings verified against aw4 main@a4944fb5 (researcher session s_1m80mxv1m56xqg08v1ra74).

## 1. Where issue.read / issue.value live

- **issue.read** — registered at `internal/tool/tool.go:979`
  (`Name: "issue.read"`, `Evidence: plan.Accepted`, `Run: issueRead`).
  Body `func issueRead(ctx context.Context, c Call) (string, error)` at
  `internal/tool/product.go:87`. The no-arg branch (empty id) calls
  `s, err := c.Cmds.Issues(ctx)` (product.go:93), then
  `un := s.Untriaged()` (product.go:100) and prints "N issue(s) waiting on you".
- **issue.value** — registered at `internal/tool/tool.go:1083`
  (`Name: "issue.value"`, `Evidence: plan.NoEvidence`, `Run: issueValue`).
  Body `func issueValue(ctx context.Context, c Call) (string, error)` at
  `internal/tool/product.go:331`. It is a **write**, not a list read:
  `c.Cmds.SetValue(ctx, ids, command.ValueSpec{...}, c.Session)` (product.go:336)
  then `return c.Cmds.ValuedText(ctx, ids)` (product.go:342).

The no-arg queue (`Untriaged()`) is the shape the brief names as insufficient: it shows
what waits on the PM (untriaged, non-duplicate, unresolved) across all of the agent's
projects, not a project's value-state.

## 2. How value-state is stored — queryable attribute, not derived from events

This is the decisive finding: a project-scoped unvalued/untriaged read is a **fast
in-memory filter over the folded projection**, not an events-table scan.

- `Issue.Value *Value` is declared at `internal/issue/issue.go:620` with the comment
  "Nil when nobody has valued it". So **unvalued ⇔ `i.Value == nil`**, an in-memory
  attribute. The value write path tests exactly this: `if i.Value != nil`
  (`internal/issue/value.go:298`).
- **Untriaged** is derivable from the same projection:
  `func (s *Issues) Untriaged() []Issue` (`internal/issue/issue.go:1290`) iterates the
  in-memory `s.byID` map and filters
  `v.Triage == nil && v.DuplicateOf == "" && v.ResolvedByCommit == nil`, sorted by ID.
  `func (i Issue) Priority() (p int, ok bool)` (`internal/issue/issue.go:655`) returns
  `0, false` for an untriaged, unassessed issue.

Both are pure in-memory filters over the folded projection. No event-log fold at read time.

## 3. Reachability from a tool body

- `func (c *Commands) Issues(ctx context.Context) (*issue.Issues, error)` at
  `internal/command/command.go:2770`, memoized per request:
  `return events.Memo(ctx, issuesMemo, ...)` (command.go:2771), with
  `const issuesMemo = "command.issues"` (command.go:2784).
- Reached from a product body via `c.Cmds.Issues(ctx)` — exactly what `issueRead` does
  (product.go:93).

### Correction to the prior graph claim

The prior claim (2026-11-21) said "Issue has `Projects []string` at issue.go:303".
That is a **misattribution**: `internal/issue/issue.go:303` is `Projects []string` on
`type Snapshot` (Snapshot starts at issue.go:291), **not** on `type Issue` (which starts
at issue.go:563). The `Issue` struct has no direct `Projects` field. Per-issue projects
must be read off a snapshot, e.g. `i.Latest().Projects`.

Consequence for the dev subtask: the new method can filter by project, but it must
derive each issue's projects from its snapshot (`i.Latest().Projects`), not from
`Issue.Projects`.

## 4. Which typed-read shape fits

A **new method on `*Issues` in `internal/issue`**, called from a `product.go` body via
`c.Cmds.Issues(ctx)`. This reuses the memoized projection and the existing
in-memory filter idiom (`Untriaged()`), and is the only shape that keeps the read off
raw SQL.

- The method filters `s.byID` by project (via `i.Latest().Projects`) and by
  value-state (`i.Value == nil`) and/or triage-state (the `Untriaged()` predicate).
- Surface choice: a filter parameter on `issue.read` (option 1) fits better than a new
  listing op under `issue.value` (option 2). `issue.value` is a write (SetValue) and
  overloading it with a list read mixes a read and a write on one tool name.
  `issue.read` is already the read tool and already branches on its arguments; adding a
  project + value-state filter is a natural extension of the existing no-arg queue.
  (Final surface naming is the tech lead's call; the storage finding — option 1 vs 2 —
  does not depend on it, since both would call the same `*Issues` method.)

## Recommendation

Implement one new in-memory method on `*Issues` (e.g. `UnvaluedIn(project string) []Issue`
and/or a combined filter) in `internal/issue`, and surface it as a filter on `issue.read`
from a `product.go` body via `c.Cmds.Issues(ctx)`. It is a fast in-memory read; no event
folding, no new index. The dev subtask touches `internal/issue/issue.go` (new method),
`internal/tool/product.go` (issueRead filter branch), `internal/tool/tool.go` (schema
for the new parameter), plus tests.
