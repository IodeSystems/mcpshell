# Design notes

Why some behaviour is the way it is. Work items are aw4 issues (project `mcpshell`), not here.

## Upstream tool calls

- **Arguments are checked before the call, but hidden options pass.** Some servers accept undeclared options on purpose, such as a `confirm` nonce for a two-phase ask → detail → continue flow. On an open schema, an unknown argument name fails only when it is a likely mistake for a declared one: the same name in another case style, or one edit away when both names are at least 5 characters (`mcp/toolkit.go` `checkArgs`, `likelyMeant`). A schema with `additionalProperties: false` rejects every undeclared name.
- **Missing required arguments are reported all at once** (`checkRequired`), so an agent does not discover them one turn at a time.
- **Types are converted only when nothing is lost** (`mcp/argtypes.go`): number/bool → string, numeric string → number, `"true"`/`"false"` → boolean, JSON string → array/object, single value → `[value]`. `5.5` for an integer fails instead of rounding. The checks skip properties without a plain `type` (anyOf/oneOf/$ref) and `null` values. Array items are not converted.
- **Escapes.** A server entry's `"unchecked": [globs]` covers tools with wrong schemas. `ns.raw("tool", {args})` skips every check for one call and returns unparsed text.
- **help is sized to save turns.** `help("ns")` lists every tool with its signature, grouped by category, up to 16 KB (`helpListAllMax`; the bench's 102-tool Acme server is 10.5 KB against 34 KB of schemas). Above that it shows categories with three names each. `help("ns.tool")` lists each parameter with its type or enum, default and description, and an error from the tool carries the same list. On the DeepSeek hosted run (2026-10-25) discovery cost 3–5 help() turns per task, and a limit stated only in a parameter description caused 6 error turns.
- **Numbers stay exact across the boundary.** Tool output and eval `vars` decode through the same parser as `parseJson`, which keeps exact numbers and key order. Arguments go upstream as `json.Number`. `JSON.stringify` of a parsed value keeps every digit but re-formats it (`1e300` → 301 digits, trailing decimal zeros dropped). Use `ns.raw` when a file must match the tool's output byte for byte.

## Language

- **`await x` is the identity, and `async` is ignored.** Tool calls return their values directly, so there is nothing to wait for. Agents write `await` and `async` by habit, and rejecting them sent them looking for a concurrency problem. An `async` function runs to the end when called and returns its value, not a promise. When it raises an error, the call returns a rejected value instead (`RejectedVal`), as a JS async function returns a rejected promise: `let p = f(); … p.catch(h)` then works. `await`, `.then/.catch/.finally` and the Promise functions handle it. Any other use raises the error there: a member read, an operator (`+`, `===`, `<`, `+=`), a template `${}`, an argument to a command or tool, also inside an array or object (looked for only in an eval that made a rejection), a condition (`if (p)`, `!p`, `||`, a filter callback), `??` and `typeof`. JS treats a promise as true and `typeof` gives "object"; here those uses are a missing `await`, and the value they needed failed. The error carries the line of the async call, or of the function when a command called it (`xs.map(f)`). One that nothing handled fails the eval at its end, as an unhandled rejection ends a Node process; without that, `f();` would lose the error that a sync call raises.
- **Every value is a settled promise.** Real promises need a scheduler that keeps JS run-to-completion while tool calls block, and agent scripts rarely depend on the ordering it gives.
  - `Promise.all`, `allSettled`, `race` and `any` take an array as well as function arguments. A function element runs in a parallel branch, as `all(() => …)` does; any other element is a value already produced. So `Promise.all([a(), b()])` gives JS results but runs the calls in order — the calls are done before `all` sees them. Use `Promise.all([() => a(), () => b()])` for parallel calls. A JS array of functions would resolve to the functions; here it calls them, which is the parallel form.
  - `race` returns the first value element without running a producer, as a settled promise wins in JS. `Promise.any` is the first producer that does not fail; the `any()` builtin stays the first truthy result. `allSettled` results carry the JS `status`/`reason` keys next to mcpshell's `ok`/`error`.
  - `.then(f, r)`, `.catch(r)` and `.finally(f)` work on any value that has no own member of that name. A chain keeps an error raised before them as a rejection: in `f().then(g).catch(h)` an error from `f` or `g` goes to `h`. The handler gets the error message string, as `catch (e)` does. An error from a function that is not `async`, outside one chain — `let p = f(); p.catch(h)` — is raised at `f()`, as a sync function throws in JS.
  - `Promise.resolve(x)` is `x`; `Promise.reject(e)` throws `e`. `new Promise(...)` stays unsupported (the error says why), and there are no timers to resolve it with.
- **`catch (e)` gets what was thrown.** `e` and a promise handler's argument are the message without the `at line` location (`ShellError.Reason`), so `e === "boom"` matches `throw "boom"`. The error the agent sees keeps the location.
- **JS habits run, with a warning.** An agent pays a turn for every refusal, so code that works in JS works here when the meaning is clear, and the eval result carries `warning: line N: …` lines (also after an error; see Diagnostics) when it may not do what was meant.
  - Declaring a builtin's name (`let all = []`) replaces it for the rest of the scope, with a warning. Refusing it was round-1 behaviour; on the hosted benchmark it cost 5 of 14 error turns. Command names (`sum`, `count`) were always declarable and do not warn: a warning on every common name would be noise.
  - Extra arguments to a command are an error, not a warning (it was a dropped argument with a warning). The error names the command, its signature, the counts and the extra values, and ends with the command's first example: `split(input: string, sep?: string|regex, limit?: number) takes 3 argument(s), got 4: the extra was 2`. The limit is the signature's parameter count (`CommandDef.MaxArgs`) in every call form: `f(a, b)`, `Ns.f(…)`, pipe (the piped value counts) and method (the receiver counts, `NativeBody.Bound`). A signature with `...` or no signature is not checked, nor is an upstream tool in `unchecked`; one object argument is named arguments. Why: a model does not read a warning after the result. `load("db", "files")` dropped `"files"`, and the next call failed for a reason that pointed elsewhere; `round(x, 2)` and `"a,b".split(",", 1)` returned a result with no sign that the argument was lost. Same rule as the XOR and NaN fixes: no silent wrong value.
  - The error must not cost a turn on correct JS, so each JS idiom with extra arguments either works or is JS-exact when ignored. Implemented: `parseInt(s, radix)` and `parseFloat` (leading number, NaN when there is none, exact for big integers), `split(sep, limit)`, `JSON.stringify` replacer (function or key list), `toPrecision`, `substr`, and `fromIndex`/`position` on `indexOf`, `lastIndexOf`, `includes`, `startsWith`, `endsWith`. Ignored, as JS ignores them (`CommandDef.Tolerate`): the `thisArg` of `map`, `filter`, `find`, `findIndex`, `forEach`, `flatMap`, `some`, `every`, the `mapFn` thisArg of `Array.from`, and the second argument of `Number`, `String`, `Boolean`, `parseFloat`. `includes` is a command of its own: `contains` has no `fromIndex`, so `filter(allowed.contains)` still gets `(element, index)` as a callback. Differs from JS: `localeCompare` with locales or options is an error (ignoring `{numeric: true}` would change the result), and `Math.round(x, 2)` rounds to two places where JS ignores the 2. Not checked: array mutators on an assignable receiver (`xs.pop(1)`).
  - Named arguments work on every callable: user functions by their parameters, commands by their signature's names, upstream tools by their schema's property names, in calls and pipes (`xs |> limit(n: 2)` — the piped value is the first argument). A null in an upstream call's position is a skipped argument and is not sent. On the second DeepSeek hosted run, `acme.list_customers(region: "West", page_size: 100)` failed 3 times with "no parameter names".
  - Reading an absent object key gives null, as JS gives undefined, and that is how optional fields are checked, so it is not warned in general. It is warned for `.length` on an object (the array is usually inside: `.items.length`) and for a key that resembles an existing one (`o.nmae`). Warnings are kept on `ExecutionLimits`, which every interpreter of one eval shares, so a callback that a command runs (the fn given to `map`) warns too.
  - `floor`, `ceil`, `trunc`, `abs` and `toFixed` are exact for exact values. `toFixed` rounds as `round` does, so `(1.005).toFixed(2)` is `"1.01"` where JS gives `"1.00"` from its float64 value: the README promises exact numbers, and two answers for one rounding would be worse.
  - `round(n, digits?)` rounds a half toward +∞ like JS `Math.round` (it was round-half-even), exactly for exact values: `round(1.005, 2)` is `1.01`.
  - ±Infinity and NaN print as `Infinity`, `-Infinity`, `NaN`, and those names are values. Go's `+Inf` did not parse back with `num()`, and an agent copied it into the next eval. In JSON (`toJson`, upstream arguments) they are null, as `JSON.stringify` gives.
  - In the MCP server a top-level `let` lasts one eval; `export` keeps a value. Reading a let, const or function of an earlier eval says so (and offers a re-declaration or `export`) instead of "Unknown command", and declaring a builtin's name at top level warns that the next eval sees the builtin. In a live dun session the model read `all` after `let all = []` in the previous eval and got the builtin function.
  - A name read in its own `let` initializer says so instead of "Unknown command". The usual cause is a line starting with `-` or `+`, which continues the previous expression as in JS (`let s = "a"` then `-s` is `let s = "a" - s`); the error names that cause when the read is on a later line.
  - JS methods mean what they mean in JS, in the pipe form too: `replace` with a string or a regex without `g` changes the first match (`replaceAll` changes all), `split()` with no separator is `[input]`, `reduce` without an initial value starts from the first element. These were replace-all, split on `,`, and start from 0. An agent writes the JS form and reads the result as JS, so a different meaning was a wrong answer with no error: `[2, 3].reduce((a, b) => a * b)` was 0. An empty array with no initial value still reduces to 0 (JS throws).
  - The ES2023 copying methods (`toSorted`, `toReversed`, `with`, `toSpliced`), `findIndex`/`findLast`/`findLastIndex`, `reduceRight`, `Number.isInteger` and the like, `Object.assign` (it returns a copy and does not change the target), `Object.groupBy` and `structuredClone` are hidden commands or aliases; `help()` does not list them. `Number` and `String` are namespaces that are also callable (`__call`), as `Array` is.
  - `typeof null` is `"null"`, not `"object"`. Null also stands for undefined here, so neither JS answer would be right for every check, and `"object"` would make `typeof x === "object"` true for a missing key.
  - A `break` or `continue` outside a loop, or with a label no enclosing loop has, is an error at the function or eval boundary. Before, it was a Go panic that ended the process.
- **A Go panic is an internal error, not a crash.** It becomes a `ShellError` with the Go stack (`Internal()`) in `withLocation`, the innermost place that knows the line, and `Shell.Eval*` converts any that get past it. Before, the MCP server re-raised it and ended, and every exported value was lost (`slice(0, -1)` did this). The agent gets the message and line; the MCP server writes the script, its vars and the stack to stderr, because the agent's copy of the script does not reach whoever fixes the bug. `try/catch`, `allSettled`, `race` and `any` do not catch an internal error: a script that handled it would hide the bug from the log.
- **A caught error is its message string.** `"x" + e` keeps working. `e.message` returns the string for JS habit. Any other unknown member on a string raises an error, because silently returning `null` hid real errors ("ERR null").
- **Bitwise ops are JS within ±2^53 and exact above it.** Numbers are exact, so a 64-bit decimal such as 14898973196205001976 is held exactly; the old ops converted the float64 view to int32, which saturates, and `p ^ d0` on 64-bit values gave 0 with no error (dun Terminal-Bench, 2026-11-07). An operand within ±2^53, where a JS Number is exact, gets ToInt32/ToUint32 results, so hash idioms (`h |= 0`, `(h << 5) - h`) and `x >>> 0` match JS. An operand above 2^53, where JS has already lost precision, gets the exact two's-complement result that JS gives for BigInt. `>>>` above 2^53 is an error: BigInt has no `>>>`.
- **BigInt is an exact integer with a mark.** `BigInt(x)`, `123n` and the results of arithmetic on them carry the mark (`NumberVal.bigint`): bitwise ops on them are always exact (`1n << 40n` is 2^40, where the JS Number rule gives 256), `/` truncates, `typeof` is `"bigint"`, `Number(x)` drops the mark. Mixing a BigInt with an integer Number is allowed, where JS raises a TypeError: models mix them, and the result is exact either way. Mixing with a non-integer is an error. `0x`/`0o`/`0b` literals are integers.
- **`^` is XOR and `|` is OR, as in JS.** They were errors with a hint, and the hint cost a turn on every first try of JS code. `|.` and `|:` stay as aliases.
- **An error names the likely cause where the parser or a value only knows the symptom.** Syntax: `{a: 1, b = 2}` says an object entry is `key: value` (JS rejects `b = 2` too; the message was "Expected '}'"); a prose line ending in `name:` parses as a label, and the error showed the next line with "check for missing operators", so it now says a label needs a loop and a note needs `//`. Runtime: a member access on null names the receiver expression (`eg` is null: a never-set variable or missing key), and a null index says it is a missing key or an element past the end. The messages are hints; none changes what runs. A `let`, `const` or `function` of an earlier eval reads as "declared in an earlier eval" (it said "with let" for all three).
- **A boolean is 1 or 0 in arithmetic.** `true + true`, `n += cond`, `-flag` and `*`, `/`, `%`, `**` work as in JS; `a() + b()` over predicates is the usual count (dun Terminal-Bench dna-assembly: `hasBsaI(x) + hasBsaI(y)` raised a type mismatch). `null` stays an error, since it stands for undefined too and JS gives different answers (`null + 1` is 1, `undefined + 1` is NaN). Comparisons (`true < 2`) and unary `+` stay unsupported.
- **`Number("1:")` is an error, not NaN.** A NaN flows silently into later math, as the XOR zeros did; the error names the string.

- **`new` works for builtin constructors only (`Date`, `Intl.NumberFormat`, `Intl.DateTimeFormat`).** `new` is a keyword with a grammar rule (`newExpr`: `new Name(.field)*(args)?`, then postfix operations, so `new Date().getTime()` parses as in JS). The callee must be an object with a `__new` member or a native function; anything else is an error that says what to use instead (`new Promise`: no timers; `new Map`/`Set`: object/array; `new Error`: throw a string). There is no `this`, so user functions cannot be constructed. `new` as a variable name no longer parses; `o.new` and `{new: 1}` still do.
- **Date is a value type, local time is UTC.** `DateVal` holds an exact int64 of ms (a JS time value, range ±8.64e15, else Invalid Date) and the local zone. The sandbox has no ambient `TZ`, so a script gives the same answer on every host: local = UTC unless the operator passes `--tz <IANA>` (or `MCPSHELL_TZ`; tzdata is embedded). A date-only ISO string is UTC and one with a time and no offset is local, as in JS. Month is 0-based in `Date`, as in JS; an out-of-range field carries (`new Date(2026, 12, 1)` is Jan 2027); `setMonth(1)` on Jan 31 gives Mar 3 as in JS. Invalid dates are NaN in arithmetic, false in comparisons, `"Invalid Date"` in text, `null` in JSON; `toISOString()` of one is an error (JS raises RangeError). `Date.now()` and `new Date()` read the host clock; the clock is not I/O and is the only source of nondeterminism besides `Math.random`.
  - Deliberate differences: printing a Date (result, template, `+` with a string) gives the ISO form, not JS's `Sat Nov 07 2026 …` form — it is what JSON, SQL text and `Dates.*` use; `d.toString()` gives the JS form. `==`/`===` compare the time value, where JS compares identity. `null` where JS has `undefined` is an error in `new Date(null)`, since it stands for both and JS gives different answers. A string that is neither ISO nor one of a dozen common text forms (`Nov 7, 2026 10:30`, RFC 1123, `7 November 2026`) is Invalid Date: V8's legacy parser guesses, and a guess is a wrong answer without a sign. `getYear`, `setYear`, `toLocaleString` zone names (`timeZoneName`) and non-en-US locales do not exist.
  - `toLocale*String` is en-US with `weekday year month day hour minute second hour12 timeZone dateStyle timeStyle`; the time uses an ordinary space before AM/PM, where recent ICU prints U+202F. `hour12: false` prints midnight as `24`, as ICU's en-US does.
- **`Dates` is the helper namespace JS lacks.** It works on the UTC calendar and takes a Date, ms, or an ISO/SQL date string; the result has the shape of the input (`"2026-11-07"` stays date-only, `"2026-11-07 12:00:00"` keeps the SQL form, a Date stays a Date), so Db text dates need no conversion. `add` applies years and months first with clamping to the month end (Jan 31 + 1 month = Feb 28), then the exact units. `range` computes each element as `start + k·step`, not from the previous element, so a month step from Jan 31 does not drift to the 28th. `businessDaysBetween(a, b)` counts `[a, b)` like numpy; weekends are Saturday and Sunday and holidays are a list (other weekends are not supported: a call that needs them is better served by a `filter` over `range`). `week` starts on Monday (ISO) unless the third argument says otherwise. `parse` fails with an error when the text does not match, where `new Date` returns Invalid Date: the format is explicit, so a mismatch is the caller's mistake, and the error names the position.
- **Number formatting is exact.** `toLocaleString` and `Intl.NumberFormat.format` round the exact `big.Rat` value half away from zero (a float-only value, from `sqrt` and the like, is taken as its shortest decimal, as ICU reads a double), so `(0.1 + 0.2)` with two digits is `"0.30"` and `(1.005)` with two is `"1.01"`. A locale other than `en-US`/`en`, and any option not implemented (`style: "unit"`, `notation: "scientific"`, `currencyDisplay: "name"`, `roundingMode`, …), is an error that lists what is supported: an ignored option changes the text without a sign. Currencies without a known en-US symbol print as `CHF 1,234.50` with U+00A0.
- **`toMarkdown(rows, opts?)`** is a command in core, so the cost is one line in the prompt. Columns are the keys in first-seen order, `columns` picks and orders, a column of only numbers (and nulls) is right-aligned, `|` is escaped, a newline is `<br>`, nested values are their JSON. An array of arrays needs `header: true` or names: guessing a header row would be wrong half the time.

## Large output

- **A truncated value is kept, not lost.** Without a file, the rest of an over-limit result was gone, and getting it meant running the eval again — every upstream call again. dun's `recap({ref, grep})` reads back a spilled text file; mcpshell holds the structured value, so it keeps it as `$rN` (the last `KeptResults` = 5) and the note gives its inferred TypeScript type (`runtime.InferType`). Querying `$r1 |> filter(…)` is more precise than grepping a text copy. A dropped ref errors with the refs still kept.
- **The type is inferred from the whole value**, not the shown part: array elements merge, keys missing from some objects are optional, a string with ≤ 5 distinct values each seen twice on average is a union of the values seen (values seen, not a schema), and objects whose keys are data (groupBy, countBy) are `Record<…>`. The type is capped at 600 bytes; past it objects list their first keys and "…N more".

- `MCPSHELL_TMP_OVERFLOW_DIR` receives the full over-limit eval output. mcpshell makes file names unique only. Scoping per session is the launcher's job: dun uses `<sessions>/<root>/overflow/<session-id>` and removes it on `ForgetSession`.
- Arrays are saved as JSON Lines and objects one key per line, so line-based `read`/`grep` can page them.

## SQL

- SQLite: the first-word check in `assertStatement` is not a security boundary. The driver runs every statement in a string, so `select 1; attach ...` passed it and created files. Three layers apply: a statement count check (`sqlSingleStatement`), an authorizer on every pooled connection (`sqliteAuthorizer`: ATTACH, DETACH, `load_extension` and non-reporting pragmas always denied; all writes denied when read-only), and `PRAGMA query_only` when read-only. The connection hook is on a private driver, not the global one, so other `sqlite` users in the process are not affected.
- Postgres: lib/pq uses the simple query protocol when a call has no parameters, and that protocol runs several statements. The same statement count check applies, with Postgres quoting (`$tag$..$tag$`, `E'..'`, nested comments). `query()` and the schema helpers run in a `READ ONLY` transaction that is rolled back, so the server refuses writes whatever the text is. Read-only mode also sets `default_transaction_read_only=on` in the DSN.
- `query()` never writes, in either mode. A writable SQLite pool switches the borrowed connection to `query_only` plus the read-only authorizer for the call and restores it after. It does not use a second pool because every `:memory:` connection is its own database.

## Db

`load("db")` gives the agent an in-memory SQLite database (`Db.*`) for its own data: group, join, rank, total. It is scratch space, so writes and DDL are allowed. Code: `toolkit/db*.go`.

- **Why a loadable and not `--sql`.** `--sql` reaches an existing database and is read-only by default. `Db` has no outside reach: no files, no network, no other database. The operator has nothing to grant, so there is no flag except `--db-max-mb`.
- **One connection.** `:memory:` with `SetMaxOpenConns(1)`: each pooled `:memory:` connection is its own database. A connection hook counts the connections the pool makes; a second one means the data was lost and every command says so (`Db.reset()` starts again). `Db.reset` closes and reopens. The state lives with the session and `unload("db")` closes it.
- **Policy.** `dbAuthorizer` is `sqliteAuthorizer(false)` plus a denial of `CREATE TEMP *`. ATTACH, DETACH, `load_extension` and non-reporting pragmas are denied, so the agent cannot raise `max_page_count`. Temp objects live outside the size cap. `Db.query` switches the connection to `query_only` and the read-only authorizer for the call, as `readQuery` does for `--sql`, and switches back. One statement per call (`sqlSingleStatement`). VACUUM attaches a work database internally, so `Db.drop` lifts the authorizer for that one fixed statement. `PRAGMA temp_store = MEMORY` keeps sort spill out of `/tmp`.
- **Size cap.** `PRAGMA max_page_count` from `--db-max-mb` (default 256) at connection open. SQLite then fails with "database or disk is full"; the error names `Db.drop`, `Db.reset` and the flag. A load runs in one transaction, so a full database rolls the load back. Not capped: sort and cursor memory of one query, and the Go copy of the rows a script passes in. RSS was about 2x the database size while loading.
- **Timeout.** 30 s per command (`sqlQueryTimeout`). A native command cannot see the eval's time limit, so the two are independent.
- **`Db.drop` runs VACUUM.** Measured on `:memory:` (300 000 rows, 10 010 pages, 40 MB): DROP alone leaves RSS at 104 MB with 10 009 free pages (the pages are reused by the next load); VACUUM returns the pages (1 page left) and RSS falls to 35 MB. VACUUM copies the database, so a nearly full database needs headroom to compact.
- **Types.** Load infers per column: all integers → INTEGER; decimals or an integer next to decimals → REAL; any string, object or array → TEXT (objects and arrays as JSON text, so `json_extract` works); `true`/`false` → INTEGER 1/0; mixed numbers and strings → TEXT. An integer beyond 64 bits, or beyond 2^53 next to decimals, is an error that names `exact`: REAL would round it.
- **CSV.** Parsed in Go with `encoding/csv`: quotes, embedded newlines, CRLF, a UTF-8 BOM. `Db.loadCsv` reads the file twice (infer, insert) so rows never sit in memory. Rules, per cell: empty or blank → null; per column: INTEGER if every cell is `-?(0|[1-9]\d*)` and fits int64; REAL if every cell is a number; else TEXT. `00123` has a leading zero, so it is text and keeps its zeros. Dates are text. A column with decimals and an integer of more than 15 digits is TEXT. A row longer than the header is an error; a shorter row is padded with null. Header names keep their case and spaces (quote them in SQL); an empty name is `colN`, a repeat gets `_2`. `.tsv` selects the tab. `Db.parseCsv` uses the same rules and returns exact numbers; `Db.toCsv` writes. Both are `Db` commands and not core: they cost prompt lines for every session. Moving them to core is a one-line change if agents want CSV without SQL.
- **File access.** `Db.loadCsv` resolves its path with the file toolkit's `confineRead` (`setFileConfiner` in `toolkit/db.go`, one call in `InstallFile`). Without the file toolkit it fails and names `--files-dir`. Only that function is shared, so the file toolkit can move behind `load("files")` without touching `Db`.
- **Functions are registered on the toolkit's private `sqlite.Driver`** (`Driver.RegisterFunction`, `RegisterCollationUtf8`). Registration is per driver, not process-global, so the `--sql` toolkit does not see them (`TestDbFunctionsAreScopedToThePrivateDriver`).
  - Aggregates and windows (Step, WindowInverse, WindowValue): `sum`, `avg`, `median`, `quantile(x, p)`, `stdev`/`stddev` (sample), `stdev_pop`/`stddev_pop`, `variance`, `var_pop`, `corr`, `covar` (sample), `covar_pop`, `mode`; scalar `dmul(a, b)`. All compute on `big.Rat`, so a window can subtract a row exactly. `quantile` interpolates linearly between ranks (R type 7, the spreadsheet PERCENTILE). `mode` breaks a tie with the smallest value. A NULL is skipped; `corr` and `covar` skip a row with a NULL in either column.
  - `sum` and `avg` replace SQLite's for this driver. The built-ins add in float64 and `sum` of text decimals converts them to float64 first. Ours add exactly (no integer overflow either) and read a text that is not a number as an error, where SQLite reads 0.
  - Result form: an integer when it is one; a REAL when its shortest form is the exact value; else the exact decimal as a BLOB (the boundary reads a BLOB as a decimal); a value with no finite decimal (1/3, a square root) is a float64. `stdev` and `corr` are exact when the root is rational (`corr` of `y = 2x` is exactly 1), else float64.
- **Numbers across the boundary.** Every number out of `Db.query` becomes an exact `NumberVal`: INTEGER by its digits (9007199254740993 stays), REAL by its shortest decimal form (`strconv 'g', -1` through `ParseNumber`, so REAL 0.1 is the exact 0.1), exact text by parsing. **REAL columns follow float64**: `SELECT 0.1 + 0.2` gives 0.30000000000000004, as in JS, and the REAL column is rounded to a float64 when stored. Numbers go in by the same rules: an integer binds as INTEGER, one beyond int64 as decimal text, a fraction as float64.
- **Exact columns (`exact: [cols]`).** Decided per column: numbers default to REAL; a column listed in `exact` is declared `DECIMAL_TEXT COLLATE DECIMAL`. The type name has TEXT affinity (it contains "TEXT"), so SQLite stores the canonical decimal string and does not convert it. The collation parses both sides as `big.Rat`, so `WHERE price > 10`, `ORDER BY`, `GROUP BY`, `=`, `min`/`max` and indexes compare by value. SQLite applies the column's TEXT affinity and collation to the other operand of a comparison, so `price > 10` or `price >= ?` with a number works. Not by value: `+ - * /` in SQL on an exact column convert to float64. `dmul` multiplies exactly; for other arithmetic, read the rows out and compute in mcpshell. A non-numeric string, `1,000`, or a value with no finite decimal (1/3) in an exact column is a load error.
  - Reading back: text of a result column declared `DECIMAL_TEXT` is parsed exactly. A computed text column has no declared type (`max(price)`, `coalesce(price, 0)`). It is read as exact decimals when the database has an exact column and every text cell has the canonical decimal form that exact columns store (`-?(0|[1-9]\d*)(\.\d*[1-9])?`). Limit: in a database that has an exact column, a computed text column of plain digits (`max(zip)`) also comes back as a number. A direct column reference is never guessed.
  - Alternatives that were rejected: BLOB storage (comparison by memcmp, and always greater than numbers); scaled INTEGER (a per-column scale, an int64 range, and comparison parameters need scaling); a numeric shadow column (two columns to keep equal, and the agent must know which to use).

## Solver

- **`solver/` is exact.** Simplex and branch and bound run on `math/big.Rat`, with no float64. The README promises exact numbers; a float LP solver would return `0.30000000000000004`-style results and tolerance-dependent feasibility ("is slack -1e-9 feasible?"). Exact rationals make every status, objective and value reproducible and checkable with `==`. The cost is speed: a dense 100x100 LP takes about 0.6 s (3.7 s under -race). The solver targets the small models an agent writes, not industrial LPs.
- **Anti-cycling:** Bland's rule in both phases. It terminates on degenerate problems (Beale, Kuhn) and is slower than steepest-edge. Two-phase simplex; redundant equality rows are dropped after phase 1.
- **MILP:** depth-first branch and bound on the LP relaxation; each node solves from scratch (no warm start). Branches on the first fractional integer variable, the floor branch first. A relaxation that is unbounded is reported `unbounded` without checking for an integer point.
- **Limits:** `MaxVars` 1000, `MaxCons` 1000, `MaxNodes` 10000, `MaxPivots` 1000000 per Solve. Size and pivot limits return `*LimitError` naming the limit. The node limit is a status (`NodeLimit`) with the best incumbent, bound and gap. `context.Context` is checked at every pivot and node. Exact numbers can grow large, so a limit on pivots does not bound the time of one pivot: the caller's context is the real time limit.

### Language API (`Solver.lp`, loadable `solver`)

- **Loadable, one command.** `toolkit.AddSolver` registers `Loadable{Name: "solver"}`; `load("solver")` defines `Solver.lp`. It has no outside effect, so no operator flag. One entry point: all input shapes go through `Solver.lp(model)`.
- **Two input forms.** Form 1 (objects) is for small models: `maximize|minimize: {var: coef}`, `subjectTo: [{x: 1, y: 2, le: 14, name?}]`, variables inferred from use. Form 2 (rows) is for data from queries: `sense`, `vars: [{id, obj?, lo?, hi?, int?}]`, `coefs: [{con, var, coef}]`, `rhs: [{con, le|ge|eq}]` (the long shape a SQL join gives). `bounds`, `int` and `limits` work in both. I did not add a third dense form (`constraints: [{terms: ...}]`): `subjectTo` rows accept `terms: {var: coef}` for names that collide with `le`/`ge`/`eq`/`name`.
- **Rules that catch typos.** A row needs exactly one of `le`/`ge`/`eq`; unknown option keys error and list the valid keys; with `vars` given, an unknown variable in any row errors and names the row; `bounds` and `int` naming an unknown variable error; the objective is given once. Errors name the row (`subjectTo[1]`, `coefs[3]`, `rhs[0] ("c")`).
- **Defaults.** Bounds `[0, inf)`. In a `vars` row, a missing `lo` is 0 and `lo: null` is no lower bound; `hi` null or missing is no upper bound; `obj` null or missing is 0. A SQL NULL `lo` therefore means "free", not 0.
- **Exact numbers in and out.** Input numbers go through `NumberVal.Exact()` to `big.Rat`; a float-only value (`Math.sqrt(2)`) is refused with an error, not rounded. Output uses `runtime.NumRat`: integers collapse to int64/big.Int, other values stay exact `kRat`. A non-terminating value such as 1/3 is exact inside the number (`r.values.x == 1/3` is true, arithmetic stays exact) and only its display rounds to 34 digits, as everywhere in mcpshell. Because a printed 0.3333... hides that, the result adds `fractions: {objective: "20/7", values: {x: "9/7"}}` (p/q strings) when any number is not an integer.
- **Result shape.** `status` is `optimal|infeasible|unbounded|node_limit` (underscore, not the Go `node-limit`). `objective` and `values` are null without a solution; `node_limit` carries the best incumbent plus `gap` and `bound`. `constraints[].active` is slack == 0.
- **Time.** `Solver.lp` runs `Solve` under a context bounded by the eval's remaining time (`ExecutionLimits.Remaining()`); a goroutine also cancels it when the eval is cancelled. The step counter does not advance inside `Solve`, so the context is the only time check. A timeout errors naming the limit and how to raise it (`ExecutionLimits.RaiseHint`). `limits.nodes` is the way to get a best-so-far answer instead of an error. `limits.vars`/`constraints`/`pivots` raise the Go limits; a hit error names the option.

## Route

- **Status rule.** `optimal` only when proven: Held-Karp (exact DP), or a heuristic result that meets its lower bound on integer costs. A heuristic result is `feasible` and has `bound` (a proven lower bound on the optimum) and `gap = (cost - bound) / cost`. A VRP with unassigned stops is `infeasible`; it returns the routes it has, each unassigned stop with a reason, and `bound`/`gap` null. A VRP is not `optimal` except with no stops or when the bound meets the cost (objective `vehicles`: never, because the bound covers only the vehicle count).
- **`routing/` is float64 and has no runtime dependency.** Haversine and euclidean distances are irrational, so exact arithmetic is not possible for them. The context stops each search; a stopped search returns its best result with `Stopped` set. Shortest paths (`ShortestFrom`, `ShortestPath` with an optional heuristic, `KShortest`, `DenseShortest`) take a plain adjacency list (`Graph`), for reuse by graph algorithms.
- **Exact inputs give exact costs** (`toolkit/route_num.go`). Each unit dimension (distance, time, load) is checked: when every value is exact (integer, decimal, fraction), the values are scaled by the common denominator to integers, and the search runs on integer-valued float64, which adds without error below 2^53 (the check uses the largest value times the number of terms). Reported numbers are exact rationals (`0.1 + 0.2` legs give `0.3`). One float value (haversine, `Math.sqrt`) makes the dimension float64. A denominator over 2^40 or a sum near 2^53 also falls back to float64. Integer costs also let the bound round up, which can prove a heuristic tour optimal.
- **TSP.** Held-Karp up to 16 nodes by default (measured on one core: 13 nodes 2 ms, 16 nodes 20-30 ms, 18 nodes 0.1 s); `exact: true` up to 20 (2^19 x 19 entries, ~90 MB, checked against the memory limit). Above: nearest neighbour, then 2-opt and Or-opt (segments of 1-3, forward or reversed) on 10-nearest-neighbour candidate lists, then iterated local search with double-bridge kicks and a seeded RNG (default kicks: 300 to 50 nodes, 100 to 200, 30 to 1000, 5 above). Same seed, same result, unless the time limit stops it. Asymmetric matrices use prefix sums for the reversed-segment cost. Open paths use a sentinel end node with cost-0 arcs.
- **TSP bound.** Held-Karp 1-tree bound with subgradient steps on `min(c(i,j), c(j,i))`: a valid bound for symmetric and asymmetric costs. A fixed-end path sets `w(start, end) = 0`; a free-end path adds a dummy node at cost 0 to all. Any penalty vector gives a valid bound, so a stopped subgradient still gives one. Measured on random plane points: gap 0.04-4.7% for 50-200 nodes (open paths are higher: the dummy node weakens the bound); 200 nodes take 0.17-0.27 s with the bound. Asymmetric bounds are weaker.
- **VRP.** Clarke-Wright savings (merges kept only when some vehicle can run the route), routes assigned to vehicles largest load first, cheapest insertion for the rest, then local search: relocate (segments of 1-3) next to a nearest neighbour or onto an empty vehicle, swap, 2-opt*, intra-route 2-opt, and route elimination. Then ruin and recreate (remove a stop and its nearest routed neighbours, reinsert) with a seeded RNG (default 200 rounds to 30 stops, 50 to 150, 20 to 500, 5 above). The plan compares by unassigned count, then vehicles used (objective `vehicles`), then cost. Each candidate route is checked in full (capacity, windows, vehicle window, maxTime, maxDist). Measured: 100 stops, 10 vehicles 0.25-0.5 s. On random instances with windows, the stops left unassigned were the ones no vehicle can reach in time alone.
- **VRP time.** A vehicle leaves at its window open, or later so that it reaches the first stop when that window opens. Service starts at `max(arrival, open)` and must start by `close`. `time` is `back - depart`, waiting and service included. Time comes from `times: matrix`, an edge `time` column, `distance / speed`, or the distance itself (then windows are in distance units).
- **VRP bound** (cheap, often weak: ~40% gap on random 100-stop instances). The largest of: each stop entered once by its cheapest arc plus at least kmin arcs into end depots (and the same for arcs out); for each stop the shortest round trip from a depot; the radial bound `sum(demand_i * r_i) / max capacity` (`r_i` = shortest start-to-i-to-end). Objective `time` adds the service times. Objective `vehicles`: kmin, the fewest largest capacities that hold the total demand. No exact VRP: an exact MILP with windows in the rational solver is too slow for more than a few stops, and two methods would double the tests.
- **Costs in.** Points `{id, lat, lon|lng}` (haversine, mean Earth radius 6371008.8 m, `units` m/km/mi) or `{id, x, y}` (euclidean, manhattan), a matrix `[[...]]` with `ids` or the `{ids, matrix}` that `Route.matrix` returns, or edges `{from, to, dist|time}`. Edges are two-way unless `directed: true`; a given reverse row wins, so asymmetric costs work. A missing pair costs the shortest path through the other nodes; no path is an error. Extra columns on data rows (from a query) are ignored, but a key one edit from a known key is an error (`demnad`). Option objects refuse unknown keys.
- **A\*.** `Route.path` with `points` next to `edges` uses the straight-line distance times `min over arcs of weight / straight line`. That heuristic is consistent in any units (time or distance), so A* gives the Dijkstra answer.
- **Time limit.** A search runs under a context of 90% of the eval's remaining time (the script can still use the result), or `timeLimit` ms. When it stops, the result is the best found, with `stopped: "time"` and a `note:`; it is not an error. Eval cancel is an error. A stop while the matrix is built is an error (no result exists yet).
- **Limits.** Dense matrices up to 5000 nodes (`routing.MaxNodes`), checked against the memory limit before allocation; `Route.matrix` output is checked too (about 64 B per matrix entry, 600 B per row). Up to 1000 vehicles; k shortest paths up to 100.
- **Not modelled.** Road networks (no built-in service; an operator can compose an upstream such as an OSRM table service via `--connect` and pass its matrix), traffic or time-dependent travel times, pickup-delivery pairs, multiple time windows per stop, breaks, multiple depots per route, split deliveries.

## Limits

- **`extendLimit` stops at operator maximums.** `extendLimit({timeout: 1e12, steps: 1e15})` removed every limit, so model code could hang the host. Each limit has a cap that only the operator raises: `--max-limits steps=N,timeout=60s,callDepth=N,outputBytes=N`. Defaults: steps 20,000,000 (20x of 1,000,000), timeout 300 s (10x of 30 s), callDepth 2048 (8x of 256; deeper recursion costs Go stack for each frame), outputBytes 1,000,000 (16x of 64,000). A value over the cap is an error that names the cap and the flag. It is not clamped: a clamped limit makes the script fail later with an error that does not match what it asked for, and the agent cannot know. A limit-hit error suggests at most the cap, and at the cap it says it cannot be raised. The eval `limits` argument is checked against the same caps. A cap below its default is raised to the default. Limits and caps reset on each eval (`Reset`), and a forked branch copies the caps.

## Diagnostics

- **One block, one channel.** The only text that reaches the model for sure is the eval result. MCP clients such as dun do not show server instructions or logging notifications to the model. So every fact for the agent goes into one block at the end of the result, after a blank line, one typed line per fact: `warning:` (the language warnings, text unchanged), `note:` (a toolkit's notice), `profile:` (per-line cost), `limits:` (a limit hit or near). It follows a value and an error alike. `Diagnostics.Format` (`runtime/shell.go`) is the one writer; `FormatWarnings` stays for the bench.
- **Notes.** A toolkit calls `Shell.Note(text)` while its command runs, for a fact the agent should act on, such as `db 212/256 MB — Db.drop(t) or unload("db") frees it`. Notes are per eval and deduped by text, as warnings are. Notes from a parallel branch are lost, as its warnings are (`Fork` makes new limits).
- **`profile: true`.** Attributes the steps of the whole eval to source lines (`StartProfile` before the code, `StopProfile` after). The block gives the total, then the top 5 lines as `profile: line N: S steps (P%)`, lines under 1% left out. Parallel branches have their own limits and are not counted, as before.
- **`limits: {…}`.** Applied after the per-eval reset and before the code (`ExecutionLimits.Set`), so it lasts one eval. A value over an operator maximum is an error before the code runs, as `extendLimit` gives; it is not clamped (see Limits). Unlike `extendLimit` it may also lower a limit. `timeout` is ms, or a duration string. An unknown key or a non-integer is an error.
- **`limits:` line.** Reported when a limit was hit or at least 80% used: `limits: steps 850000/1000000 (85%), time 26000/30000ms (86%)`, or `steps 1000000/1000000 (hit)`. It covers steps, time, call depth (the peak) and output bytes. Time is checked every 1000 steps, so a time-out can show a little over the limit.
- **Why eval arguments, not in-language `profile()`/`limits()`.** The agent had to know the command, wrap code in a function (`profile(() => …)`) and run the eval again after a limit hit with `extendLimit` as the first line. An argument is in the tool schema, which every client shows to the model, costs no prompt text (the two commands and a syntax line were 425 bytes of the prompt) and needs no change to the code. A limit-hit error in MCP mode names the argument (`re-run with the eval argument limits: {steps: N}`); the CLI names `--limits steps=N`; the REPL and embedding hosts keep `extendLimit` (`ExecutionLimits.Hint`).
- **Compatibility.** `profile`, `limits` and `extendLimit` stay callable but hidden (not in `help()` or the prompt), because code written from habit or conditional raises (`if (big) extendLimit(…)`) uses them. Inside an eval that already profiles, `profile(fn)` runs `fn` and reports no lines: the block has them.
- **CLI.** `mcpshell --profile --limits steps=N,timeout=60s '<code>'` (also before `-f`), parsed by `runtime.ParseLimitSpec`, like `--max-limits`. The flags must come first. The block goes to stderr. The one-shot forms have no `--max-limits`, so an over-maximum error names a flag that exists only for `mcp`.

## Memory

- **What is limited.** Bytes of Go heap objects, `limits: {memory}` (bytes or "512MB"), default 1 GB, operator maximum 2 GB (`--max-limits memory=4GB`; MB/GB/KB suffixes, 1024-based). Same rules as the other limits: over the cap is an error, one eval, reset on the next. The steps limit does not bound memory: `range(1e10)` is one step, `s = s + s` is a few.
- **Why live heap after a GC.** The heap read from `runtime/metrics` (`/memory/classes/heap/objects:bytes`) holds live objects plus garbage the collector has not freed yet. A script that makes much short-lived garbage passes the limit between two GCs without holding the memory. So an over-limit read forces one `runtime.GC()`, reads again, and fails only if the heap is still over. Forced GCs from the periodic check are 100 ms apart at least, so a live heap near the limit does not cost a GC for each check. `/gc/heap/live:bytes` is not used: it changes only when a GC ends, so it is stale for the whole interval.
- **Where it is checked.** (1) `Step`, every 4096 steps, next to the timeout check. One metrics read costs ~0.7 µs; on a tight `for` loop the on/off difference is inside the noise of the run (BenchmarkMemoryCheckOn/Off in `runtime/memory_test.go`, about 700 ms each). (2) Natives that allocate from a number the script gives are refused before they allocate, with an estimate against the heap that is left: `range`, `Array(n)`, `toArray({length})`, `repeat`/`padStart`/`padEnd`, array spread, string `+` from 1 MB. The error says what it needs: `range(0, 10000000000) needs ~745 GB`. (3) A command that returns a big array (65,536 elements) or string (1 MB) reads the heap after it returns. Outputs that grow with their input (`concat`, `flat`, `map`) have no estimate; a doubling loop would pass the limit in few steps, so these are caught after the allocation. The heap can pass the limit by one result.
- **Soft GC target.** Servers and the CLI set `debug.SetMemoryLimit` to the eval's limit. Without it GOGC lets the heap grow to twice the live size before a GC, so a 1 GB live heap could use 2 GB of RSS before the check sees garbage; with it the collector works harder when the heap nears the limit and RSS stays near the limit. The target is the limit, not 90% of it: at 90% a live heap between 90% and 100% made the collector run all the time. A set `GOMEMLIMIT` is the operator's and stays. Embedding hosts leave it off (`ExecutionLimits.GCTarget`), as it is process-wide.
- **The report.** On overrun (error) and at 80% or more at the end of an eval (`note: memory …`), the text gives heap used and limit, then the holders across evals, largest first, each with an estimated cost and the action that frees it, then `this eval: the rest`. Holders: kept results (`forget("$r2")`), exports (`export rows = null`), and the loadables whose closer implements `runtime.MemCoster` (`MemCost() {Bytes, Detail, Free, OffHeap}`): `db` (page_count × page size; tables from `dbstat`; `Db.drop("t") or unload("db")`), `graph` (nodes and edges × a flat cost, plus a walk of the properties; `unload("graph")`). `browser` reports nothing. The report is not shown when the eval itself failed with the memory error: the error has it.
- **`forget("$rN")`** drops a kept result. It had no other way out before; the last 5 stayed until pushed out. It is named after what it does, as `unload` is for toolkits.
- **Estimates.** A value walk adds string bytes, array slots, objects and number structs, and counts a shared array, object or long string once. An object's size is measured, not guessed: a Go map allocates a ~300 B group for its first key, so a small object is ~420–550 B and 2M rows of `{i, s}` take ~1 GB (`objectSize`, go1.27 amd64). An array longer than 2048 is sampled (1024 elements, scaled), so one large export does not use the walk budget: before, a 1.5M-row export was walked to a third, reported at a third of its size, and the rest showed as `this eval`, which pointed the agent at the wrong holder. `TestEstimateSizeNearMeasured` keeps the estimate within 0.6–1.6× of the measured heap (measured: 0.93–1.01; empty objects 0.78). The walk stops after 2,000,000 values; the line then says `≥~`. The estimate misses interpreter state that is not a global (closures, the call stack, locals of the running eval: they are in `this eval`) and everything outside the Go heap.
- **Off the Go heap.** SQLite (`modernc.org/sqlite`) allocates its pages outside the Go heap, so `Db` data is not in the limit. It is capped by `--db-max-mb`, and the report lists it as `off-heap, not in the limit` so the agent can still free it. The browser is another process. The SQLite page cache and `temp_store = MEMORY` are inside the db figure only as far as `page_count` shows them. RSS of the process is the heap plus these.

## Build

- `make vet`, not `go vet ./...`. ANTLR ends every rule in the generated `parser/` with a dead `goto errorExit` so the label is always used. vet reports each one as unreachable code (69 reports, the same at v0.4.1). These reports cannot be acted on in a generated file.
- `make release DIST=<dir outside the checkout>`, run from a clean checkout of the tag, so the build stamps the tag as the version. Go stamps a pseudo-version when the tree is dirty. v0.5.0's `.gitignore` has no `/dist/`, so output written into that checkout would make it dirty. Writing outside the checkout avoids that.
- Release builds use `-tags release`. dun classifies a binary from its build info: a `vcs.revision` without the release tag reads as "built from a checkout", so v0.6.0's tarballs showed in `dun doctor` as a checkout at de7d047 although their module version was v0.6.0. `-trimpath` drops `-ldflags` from the build info, so the tag is the only mark that survives. No source file uses the tag.

## Loadable toolkits

- **Two tiers.** In-process toolkits with no outside effect are *agent tier*: always loadable (`Shell.AddLoadable`), not installed at start, listed in `help()` and the prompt, installed by `load("name")`. Toolkits that reach outside the process are *operator tier*: the flag (`--web`, `--files-dir`, `--browser`) permits the toolkit and `load("name")` installs it. Without the flag the toolkit is registered with `Loadable.Disabled = "--flag"`: not advertised, `load` fails naming the flag, and calling its commands gives the same message. The agent cannot widen what the operator permitted; the flag still decides what the toolkit can reach (the files root, read-only). `--sql` is not a loadable: it stays installed at start, as it is per-database config.
- **Which toolkits.** `graph` is agent tier. `web`, `files`, `browser` are operator tier. `profile`, `limits` and `extendLimit` stay in core, hidden (see Diagnostics). `xor` is a hidden alias of the `^` operator (hidden like the ES2023 copy methods: callable, not listed).
- **Why not install all at start.** Each toolkit adds its commands to `help()` and the prompt. A loadable costs one line until an agent needs it.
- **`load` is overloaded** and lives in core. A bare argument (no `/`, no `.`) that names a registered loadable loads the toolkit. Anything else evaluates a `.mcpshell` file through the loader the file toolkit sets (`Shell.SetFileLoader`, confined to its root). If `--files-dir` permitted the toolkit but it is not loaded, the path form loads it first. If not permitted, it errors naming `--files-dir`. A loadable named like a file therefore shadows it. Loading again is a no-op that returns the same summary.
- **Registration, not a flag, decides.** `Loadable{Name, Summary, Guide, Namespaces, Install}` is a Go value. `Install` registers commands through `Shell.Register`; `Shell` records what it adds while `Install` runs, so `unload` removes those commands, their emptied namespace globals and guides, and closes the returned `io.Closer`. A failed `Install` is rolled back.
- **Stale references fail clearly.** Commands registered by a load are wrapped: after `unload`, a kept `Ns.cmd` (an exported `let f = Ns.cmd`, `$rN`) errors `toolkit "x" was unloaded`, and a reload does not revive it. A bare `Ns` (global removed) gets the "call load first" hint.
- **The first load returns the usage.** `load("x")` returns one line per command with its signature, then the toolkit's guide; a second load returns one line. In the dun Terminal-Bench trials (2026-11-07) 0 of 16 eval calls called `help()`; models guessed names instead. The usage costs tokens once, in the result of the call that needs it, not in every prompt.
- **Errors from a loaded command end with the right call.** The load hook wraps each command: a script error it raises gets `Usage: Ns.cmd(signature)` (left out when the error already shows that signature) and `Usage: e.g. <first example>`. After the load result, errors are where a model learns a toolkit.
- **`Files.*` and `Graph.*` alias the bare commands.** The file and graph toolkits register bare commands (`read`, `ls`, `addNode`); db and solver use a namespace (`Db.query`). In dun full6 (2026-11-08, GLM-5.3-Flash) a model wrote `Files.read` 3 times and `files.ls` 7 times in one trial, copying the `Db.query` pattern. The capitalized namespace is a hidden alias, so it runs. A wrong-case name (`files.ls`, `db.query`) is not aliased, because `files` is a common variable name; when it is not defined, the error gives the right form. The load usage block cannot prevent this: models call `load()` and the first command in one eval, so they read the block only after the error.
- **Not-loaded errors.** An identifier that is a not-loaded loadable's namespace errors with `call load("name") first` before the unknown-command path (`visitIdentifierExpr`). Operator-denied loadables (`--no-load`) get the plain unknown-command error and are not advertised. The hint also covers a loadable's global command names (`Loadable.Commands`: `addNode`, `read`, `glob`), because graph and files commands are not namespaced. The toolkit constructors in `toolkit/loadables.go` fill `Commands` by installing into a scratch shell, so the list cannot drift.
- **Prompt does not change mid-session.** `ToPrompt` lists every allowed loadable, loaded or not, so the line is the same before and after a load. A changed prompt invalidates the model's KV cache. The prompt is built once at start. Only `help()` output changes after a load (its Available line lists the not-loaded ones).
- **Load state is session state.** `mcp.Server` runs one `Shell` for the whole session, so a load lasts like `export`. `mcp --no-load a,b` denies and hides loadables (`Shell.DenyLoadables`, independent of registration order). The CLI one-shot and REPL modes take code as arguments, so they have no flag.
- **Concurrency.** The MCP stdio loop handles one request at a time, so evals do not overlap. Inside one eval, `all`/`allSettled`/`race` and `Promise.all` with function elements run branches on goroutines, and a branch can call `load`, `unload` or `help`. `CommandRegistry` therefore has an `RWMutex` on every exported method; `Environment` already has its own lock. `load`/`unload` are serialized by a separate mutex. `TestLoadRace` runs these in parallel; run the suite with `-race`.
- **Advertising over MCP.** Some clients (dun) show the model only the `eval` tool description, not the server instructions or `ToPrompt`. The description is `runtime.ToolDescription` plus the Available line, fixed at the first `tools/list` (`Server.evalDescription`), so it is the same before and after a load. It lists only allowed loadables: `--no-load` and operator-tier toolkits without their flag are left out.
- **Over-limit output stays pageable.** The overflow note tells the agent to `read()`/`grep()` the spill file. A read-only file toolkit on `MCPSHELL_TMP_OVERFLOW_DIR` is therefore installed at start, whatever `--files-dir` says. The alternative, a note that says `load("files")` first, costs one turn per spill and cannot work without `--files-dir`. Its file loader is cleared, so `load("x.mcpshell")` needs the real toolkit. `load("files")` replaces these commands with the full toolkit (with the overflow dir as an extra read root), and `unload("files")` puts the reader back. Cost: with `--files-dir` set and files not loaded, `read("project/file")` hits the reader, which resolves the path inside the overflow dir and errors there.
- **CLI keeps everything installed.** One-shot, `-f`, stdin and REPL are for humans: `newShell` installs core, math, web, graph and files (cwd) directly, with no loadables and no flags. `load("graph")` there is not a toolkit name, so it does not work. `--browser` and `--sql` are MCP-only, as before.
- **Prompt size** (bytes of `ToPrompt(false)`; `mcpshell mcp --prompt` prints it for a flag set): CLI 11510 → 11466 (`xor` hidden). `mcp` with no flags 9042 → 8173. `mcp --web --files-dir . --browser` 12594 → 8431.
